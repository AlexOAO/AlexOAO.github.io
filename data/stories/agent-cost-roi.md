## 結果

**銀行要推出四個業務用的 AI Agent。我替每一個都做了專案原型，再用同一套方法算它們的成本和效益。** 有了原型，業務單位在砸大錢之前，就能先看到 Agent 實際怎麼運作。有了這套成本效益方法，四個 Agent 第一次能放在同一張表上比較；上線後，也能追蹤當初的預估有沒有做到。

- 四個原型，各自對應客戶旅程的一個階段：獲客、交易、服務、經營。
- 一套共用的成本效益框架，加上兩類可以追蹤的指標：業務比率和實現比率。
- 每個 Agent 的基準還在建立中，細節請看下方的子專案。

## 為什麼要做

**銀行的目標，是用 AI Agent 把客戶的整段旅程串起來。** 這段旅程從客戶第一次接觸銀行、申辦、使用服務，一路到長期的財富經營。每一段交給一個 Agent，四個 Agent 共用客戶資料，前一段的成果再接到下一段。

**資源要先給誰，得先回答兩個問題：它實際會怎麼運作？它值不值得做？** 麻煩的是，四個 Agent 服務的人不同、部署的方式不同，花錢的地方也不同。

## 四個 Agent 與客戶旅程

**第一段｜智慧獲客：[貸款助理（Sales Agent）](project.html?id=agent-loan-assistant)。** 目標是找對客戶、提高成交。它在數位申辦平台和社群上直接和客戶聊：介紹產品、帶客戶申辦，並在授權範圍內議價。超出授權的條件交給主管，它也不能保證貸款一定核准。在授權範圍內它自己運作，遇到例外才由人處理（human-on-the-loop）。它放在雲端，資料送出前會先去識別化，也就是拿掉能認出客戶身分的資訊。

**第二段｜智慧交易：[智能徵審（Credit Agent）](project.html?id=agent-credit-review)。** 目標是更快核貸、提高效率。它不面對客戶，而是幫審核貸款的徵審人員做三件事：看懂財力證明文件、檢查內容合不合理、算出年收入。每個判斷都附上理由。沒把握的案件交給徵審人員，它不做核貸決定，也不打信用分數。每一件都由人覆核（human-in-the-loop）。它同時用雲端和行內自己的機房（地端），在離峰時段一次批次處理。

**第三段｜智慧服務：[客服助理（Service Agent）](project.html?id=agent-customer-service)。** 目標是主動服務、提高滿意度。它是客服人員身邊的 AI 小幫手（Copilot）：查知識庫、先擬好回覆草稿、通話結束後寫摘要、先初步檢查服務品質。寫進紀錄的內容都要客服人員確認，它也不直接回覆客戶（human-in-the-loop）。因為要處理通話錄音，它全部放在地端。

**第四段｜智慧經營：[智富管家（App 2.0）](project.html?id=agent-wealth-assistant)。** 目標是做好財富管理、加深客戶關係。它是 App 裡的理財聊天功能：查帳戶、分析資產、介紹商品。推薦商品前，一定要先確認客戶的風險等級。它不幫客戶下單交易，也不碰密碼和驗證碼（human-in-the-loop）。它同時用雲端和地端：地端的小模型先判斷客戶想做什麼，雲端的模型再處理查詢。

## 閉環：四個 Agent 怎麼串起來

- **同一個客戶，同一份資料。** App、網銀和分行的客戶資料整合在一起。客戶不管從哪個管道進來，Agent 認得的都是同一個人。
- **決策中樞。** 交易資料，加上客戶和 Agent 聊過的內容，組成客戶的完整樣貌（客戶 360）。再由傾向模型判斷，下一步最適合提供客戶什麼。
- **回饋。** 每一段的結果都回到資料裡，讓系統越來越準，也帶出下一次商機。獲客帶進來的客戶進入交易，交易後的服務和經營，又會帶出新的需求。
- **共同的基礎。** 四個 Agent 共用集團的運算資源、AI 營運管理平台和 AI 治理。上線前的檢查請看 [AI 治理](project.html?id=agent-governance)，上線後的成效請看 [AI 營運成效 Dashboard](project.html?id=ai-ops-dashboard)。

## 我的角色

我做了兩件事：

- **做原型。** 四個 Agent 我各做了一個專案原型，讓業務單位先看得到、摸得到，再決定要不要投入。
- **主責成本效益。** 我設計四個 Agent 共用的成本效益框架和管理方式。業務量由業務單位提供，用量由資訊單位提供，框架、計算和比較由我負責。

## 我怎麼做

**第一階段｜原型。** 我依照每個 Agent 的使用情境做原型，把「它會怎麼運作」變成大家看得到的東西。例如智富管家的原型是一個手機網銀的 MVP，也就是功能最精簡但能用的版本，從登入、查帳戶到和 AI 聊天，都能實際操作。

**第二階段｜框架設計。** 四個 Agent 花錢的方式完全不同：有的在雲端，有的在地端；有的按通話計費，有的按案件計費。所以我用同一組公式來描述它們。成本＝業務量 × 每件用掉的資源 × 資源單價；效益＝業務量 × 每件帶來的效益 × 價值單價。兩邊都從業務量算起，所以能直接算出可以互相比較的單件成本和 ROI（投資報酬率）。在這個框架上，我定了兩類指標：

- 業務比率：AI 處理的業務 ÷ 總業務量，例如 AI 處理率、轉人工率。它回答「AI 有沒有真的在做事」。
- 實現比率：實際值 ÷ 基準值，例如業務量實現率、成本執行率、效益實現率。它回答「當初的預估有沒有做到」。

**兩種工具互相補位：大型 Agent 先算清楚值不值得，小需求先排好先後順序。** 這套三年基準，適合規模大、成本複雜的 Agent。數量多、規模小的內部需求，則用比較簡單的評分表排序：看效益、可行性、合規和成本，由 BA 或 SA 填寫。

**第三階段｜資料蒐集與試算。** 這個階段正在進行。業務單位提供業務量和效益，資訊單位提供用量。資料到齊後，我會替每個 Agent 建立三年的業務量、成本和效益基準。上線後算實現比率時，就拿這份基準當分母。

**第四階段｜制度化。** 我打算把這些指標接進分配資源的流程。上線前先提出基準，上線後定期追蹤業務比率和實現比率。實現比率低於門檻時就啟動檢討，調整資源或範圍。

為了讓這件事真的能每天看到，我做了 [AI 營運平台](project.html?id=ai-ops-platform)：它收齊四個 Agent 的實際資料，把每個 Agent 的業務規劃書（預期）和實際數字並排，算出實現比率，低於門檻就列進「需要檢討」。
