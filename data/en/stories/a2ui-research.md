## Results

**I run the A2UI research along a "technology to product" journey: find business use cases first, then confirm resources, then prove business value, and only then talk about launch.** It is now in phases 1 and 2: candidate use cases are mapped, and the PoC environment and resources are being confirmed. The next gate is the business-value checkpoint.

## Why this project

A2UI is a protocol that Google open-sourced in December 2025. It lets an AI Agent reply not only with text but with an interface: the Agent sends JSON that describes components and data, and the front end draws it with its own pre-approved components. Because the Agent sends data, not code, it cannot run arbitrary programs; it can only pick from the front end's component list.

For a bank, this solves a real problem: wealth information in a long block of text is hard for customers to read, but letting AI generate web code would never pass a security review. A2UI sits in between: **the AI decides how the screen is laid out; the bank decides which components exist.**

## My role

I lead this research. The question I must answer: can this technology become a product feature of the bank?

## What I did

**Phase 1 | Business use cases.** The first question in technology research is not "what can the technology do" but "where can we use it". With the Wealth Assistant as the main case, I mapped three candidates:

- Asset overview: cards and charts that show a customer's asset allocation, instead of a long text.
- Product comparison: a comparison table of the funds a customer asks about.
- Data entry: forms that help a customer complete items such as the risk profile questionnaire.

The boundary comes first too: under the pre-launch check, the Wealth Assistant may not execute transactions, so A2UI is used only for information display and data entry, with no order buttons.

**Phase 2 | Resources.** I listed what the PoC needs: environment requirements and technical specifications, Azure AI Foundry and token applications, connection to the IT test environment, and the list of front-end components allowed. What A2UI can draw depends on which components the bank approves. In progress.

**Phase 3 | Value check.** Technical feasibility is only the entry ticket. At the checkpoint, the business units must confirm: which use case is worth doing first? Which metric defines success?

**Phase 4 | PoC.** After a use case is chosen, build it in the test environment and apply the Guardrails and pre-launch checks: an interface generated by an Agent must also pass output-layer validation.

**Phase 5 | Productize.** After the PoC passes, work with the Wealth Assistant team to put A2UI on the product roadmap.
